# Проверка VK API — результаты и ограничения

**Статус:** выполнено 2026-11-17 (обязательный предварительный этап, ТЗ раздел 3)
**Условия:** реальные запросы к `https://api.vk.com/method/` с **сервисным ключом
приложения** (`VK_ACCESS_TOKEN`), `VK_API_VERSION=5.199`, Python 3.13, без токена
личной страницы.

## 2. Метод `newsfeed.search`

### 2.1. Доступность с сервисным ключом

**Результат: ДА.** Метод успешно вызывается с сервисным ключом приложения.
Ошибки авторизации (`error_code`: 5, 15, 27) не возникали.

Пример успешного ответа (сокращён):

```json
{
  "response": {
    "count": 58,
    "total_count": 58,
    "items": [
      {
        "inner_type": "wall_wallpost",
        "type": "post",
        "id": 6304,
        "owner_id": -238001933,
        "from_id": -238001933,
        "date": 1794908089,
        "text": "…",
        "marked_as_ads": 0,
        "post_type": "post",
        "comments": {"count": 0},
        "likes": {"can_like": 0, "count": 0, "user_likes": 0},
        "reposts": {"count": 0},
        "attachments": [],
        "donut": {"is_donut": false}
      }
    ],
    "profiles": [],
    "groups": [],
    "reaction_sets": []
  }
}
```

### 2.2. Параметры

| Параметр | Поддержка | Комментарий |
|---|---|---|
| `q` | ✅ | Обычные фразы и хэштеги (`IT`, `#IT`, `чат-бот`, `создание чат-ботов`) |
| `start_time` | ✅ | Unix timestamp, ограничивает **снизу** |
| `end_time` | ✅ | Unix timestamp, ограничивает **сверху** |
| `count` | ✅ | Максимум **200**; `count=250` → `error_code 100` («count should be less or equal to 200») |
| `extended=1` | ✅ | Возвращает `profiles` (авторы-пользователи) и `groups` (сообщества) |
| `start_from` (пагинация) | ❌ | **Не работает с сервисным ключом** — см. п.2.3 |
| `offset` | ❌ | Игнорируется |

### 2.3. Критическое ограничение: пагинация недоступна

Проверено экспериментально:

1. В ответе **никогда** не приходит поле `start_from` / `next_from`.
2. При передаче `start_from` вручную (`30`, `20`, `10`, `0`, `aaaa`) VK **молча
   игнорирует** параметр и возвращает первую страницу.
3. Параметр `offset` также игнорируется.
4. Поэтому **получить больше одной страницы по одному запросу невозможно**.

Глубина выдачи по одному запросу ограничена последними `count` публикациями:

| `count` | Возвращено | Самый старый пост в выдаче |
|---|---|---|
| 5 | 5 | ~36 мин назад |
| 30 | 30 | ~1.7 ч назад |
| 200 | 58 | ~2.8–20 ч назад (зависит от активности темы) |

При этом `start_time`/`end_time` **честно сужают** окно: за 72 часа через
6-часовые окна собрано 549 публикаций по одному запросу «Python».

### 2.4. Нестабильность порядка выдачи

Между повторными одинаковыми запросами VK может ротировать порядок выдачи:

```
req0: oldest=9964s   newest=1389s   (57 items)
req1: oldest=72885s  newest=1758s   (58 items)
req3: oldest=9964s   newest=1389s   (57 items)
```

**Вывод:** полагаться на «первую страницу» нельзя — дедупликация по
`(owner_id, post_id)` в PostgreSQL обязательна (предусмотрена ТЗ п.6.3).

### 2.5. Лимиты частоты

30 последовательных запросов подряд — **0 ошибок** `error_code 6`
(«Too many requests»). Тем не менее троттлинг в клиенте оставлен (пауза между
запросами + экспоненциальный backoff на ошибках 1, 2, 6, 9, 10).

## 3. Поля публикации в ответе `newsfeed.search`

Полный набор полей `items[]` в v5.199:

```
inner_type, type, id, owner_id, from_id, date, text,
marked_as_ads, marked_as_author_ad, author_ad, post_type,
comments {count}, likes {count, user_likes, can_like},
reposts {count}, attachments, donut {is_donut},
carousel_offset (у карусельной рекламы), reaction_set_id
```

| Поле | Назначение в проекте |
|---|---|
| `id`, `owner_id` | Составной ключ дедупликации `(owner_id, post_id)` |
| `from_id` | `author_id` (может отличаться от `owner_id` при репосте) |
| `date` | `published_at` |
| `text` | Основной текст публикации |
| `marked_as_ads` | Официальная реклама → **безусловное исключение** (ТЗ п.8) |
| `marked_as_author_ad` | Реклама автора → тоже исключение |
| `author_ad` | Блок данных об авторе-рекламодателе → тоже исключение |
| `post_type` | `post_ads` → исключение; в обычной выдаче `post` |
| `comments.count`, `likes.count`, `reposts.count` | Метрики (сохраняются, если есть) |
| `views` | В `newsfeed.search` **не возвращается** → `NULL` в БД |

**Важно (ТЗ п.8):** отсутствие `marked_as_ads` нельзя трактовать как «не реклама»:

* `marked_as_ads == 0` → `ad_flag = "no"`;
* `marked_as_ads == 1` / `post_type == "post_ads"` / непустой `author_ad` →
  `ad_flag = "yes"` → статус `rejected_ad`;
* поле **отсутствует** в payload → `ad_flag = "unknown"` → консервативный путь:
  дополнительная проверка контентом (LLM), при неопределённости — не отправлять.

## 4. Прочие проверенные методы (вспомогательные)

| Метод | Сервисный ключ | Назначение |
|---|---|---|
| `users.get` | ✅ | Имя автора публикации |
| `groups.getById` | ✅ | Название сообщества, screen_name |
| `wall.getById` | ✅ | Точная загрузка конкретных постов, повторная проверка рекламных полей |
| `wall.get` | ✅ | Записи одной стены — **не** используется как глобальный поиск |

> `wall.getById` возвращает те же рекламные поля (`marked_as_ads`,
> `marked_as_author_ad`, `author_ad`), поэтому может служить для повторной
> проверки подозрительных публикаций.

## 5. Принятые технические решения

1. **Основной метод поиска — `newsfeed.search`**: только он даёт глобальный
   поиск по ленте ВКонтакте. `wall.get` по конкретным группам **не** подменяет
   глобальный поиск (прямо запрещено ТЗ раздел 3).
2. **Стратегия выборки — rolling window:**
   * окно `[watermark − overlap, now]` (длина окна и перекрытие настраиваются
     в `config/filters.json`);
   * `count = 200` (максимум);
   * один запрос на каждый маркер-запрос, без пагинации;
   * watermark + перекрытие компенсируют ротацию выдачи и пропуски.
3. **Дедупликация:** `UNIQUE (owner_id, post_id)` + `text_hash` в PostgreSQL.
   Повторно найденные публикации не попадают в LLM (ТЗ п.6.3).
   Хеш считается по нормализованному тексту **с учётом длины**: наблюдение из
   реальной выборки — разные сообщества публикуют текст с одинаковым URL
   (`https://habr.com/ru/articles/11088756/`), и без учёта длины такие
   публикации ошибочно считались дублями.
4. **Обработка ошибок VK:** экспоненциальный backoff, максимум 5 попыток,
   таймаут запроса, фиксация ошибок в `monitoring_runs.errors`.
5. **Ссылка на публикацию:** `https://vk.com/wall{owner_id}_{post_id}` —
   корректно для отрицательных `owner_id` (сообщества).
6. **Ограничения VK не обходятся:** никаких неофициальных схем авторизации,
   сторонних токенов и обходов лимитов.
