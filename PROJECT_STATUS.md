### Найденные и исправленные проблемы

1. **Уникальный индекс `text_hash` ронял пакет.** Реальная ситуация: одно
   рекламное сообщение («До прямой линии Фёдора Щукина…») разослано 6 разными
   сообществами. Второй INSERT падал с `UniqueViolationError`, и **весь пакет
   терялся**. Решение: конфликтующие хеши вычисляются заранее, дубль
   сохраняется без хеша, публикация не теряется.
2. **`ON CONFLICT` с партиальным индексом.** `ON CONFLICT (text_hash)` не
   принимает партиальный индекс, `ON CONFLICT ON CONSTRAINT` — тоже (у индекса
   нет одноимённого constraint). Проверено на живом PostgreSQL, от этого
   подхода отказались в пользу предварительной проверки.
3. **Хеш без учёта длины давал ложные совпадения.** Тексты, состоящие из
   ссылки + служебного хвоста, после нормализации становились пустыми и
   получали одинаковый хеш. Теперь длина исходного текста входит в хеш.
4. **`known` считался неверно** для повторно найденных публикаций —
   исправлено: повторная находка всегда инкрементирует счётчик.

## Этап 8 — Отказоустойчивость цикла (✅ выполнено)

Выявлено при реальном сбое: цикл шёл 20+ минут (351 публикация, LLM-этап),
машина выключилась — и **вся работа пропала**. В БД не осталось ни записи
о прогоне, ни статусов публикаций, ни оплаченных LLM-результатов.

### Причины

1. `monitoring_runs` создавался в памяти и не коммитился до самого конца
   цикла — при обрыве запись исчезала вместе с транзакцией.
2. Все статусы публикаций (`approved`/`rejected_llm`) и `post_analysis`
   жили в одной транзакции и откатывались целиком.
3. Redis-лок имел TTL 3600 с без продления: цикл дольше часа терял
   блокировку, и следующий запуск мог стартовать параллельно (нарушение ТЗ п.5.1).
4. Зависший `running`-прогон оставался в этом статусе навсегда, искажая историю.

### Реализованные изменения

| Файл | Изменение |
|---|---|
| `app/scheduler/monitoring.py` | `_save_progress()` — commit каждые 5 публикаций; `reap_stale_runs()` — закрытие зависших прогонов; commit записи `run` до долгих этапов; `_rollback_quietly()` |
| `app/db/redis_client.py` | `cycle_lock()` + `_LockHeartbeat` + `extend_lock()` — продление TTL блокировки |
| `app/scheduler/runner.py` | `reap_stale_runs()` при старте сервиса |
| `tests/test_cycle_resilience.py` | **новый** — 4 теста |
| `tests/test_redis_lock.py` | +3 теста (продление, эксклюзивность, heartbeat) |
| `docs/architecture.md` | принцип №3 «Отказоустойчивость к обрыву» |

### Ключевые решения

**Промежуточные commit'ы.** Прогресс фиксируется каждые `SAVE_EVERY = 5`
публикаций на этапах фильтрации и LLM. Обрыв процесса теперь теряет максимум
5 публикаций вместо всей партии, а оплаченные запросы к модели сохраняются.

**Heartbeat блокировки.** Каждые `TTL/3` секунд фоновая задача продлевает
ключ в Redis, если он всё ещё принадлежит нам (Lua-скрипт проверяет токен).
Цикл на 3 часа больше не «отпускает» блокировку на 2-м часу.

**`reap_stale_runs(older_than_hours=3)`.** При старте сервиса прогоны
в статусе `running` старше 3 часов помечаются `failed` с причиной
«цикл прерван без завершения». Учтено, что он читает БД до `load_watermark`.

**Очередь не теряется:** публикации сверх лимита остаются в статусе `new` и
берутся первыми в следующем цикле (`_pending_new`). Публикации, на которых
LLM уже вернула ошибку, повторно не обрабатываются — иначе «битый» текст
тратил бы токены каждый час.

### Дополнительно исправлено при деплое

1. **Зависшая блокировка после убийства процесса.** Пересборка контейнера
   убивала цикл, не снимая ключ в Redis; при TTL 3600 с следующий плановый
   запуск пропускался. TTL снижен до **900 с** — heartbeat продлевает его
   каждые 5 минут, пока цикл жив, а убитый процесс блокирует максимум 15 минут.

2. **Осиротевшие записи `running`.** Прогоны #1 и #2 висели в `running`
   после пересборок; `reap_stale_runs` закрывал их только через 3 часа.
   Теперь при старте каждого цикла (под заведомо удерживаемой блокировкой)
   все оставшиеся `running` закрываются сразу — проверено: #1 и #2 получили
   статус `failed` в момент старта #3.

3. **Тесты зависели от состояния локальной БД.** 5 тестов `test_telegram_queue`
   падали из-за pending-уведомлений, оставшихся от прерванных прогонов
   (`process_due` обрабатывает все pending). После очистки БД — 328 из 328.

## Исправление проверки комментариев (⚠️ был дефект)

Заказчик прислал публикацию `-65967716_947` («Suno снимет клип на вашу песню»):
у неё **«Автор ограничил возможность комментирования»**, но она пришла в
Telegram. Разбор показал, что проверка комментариев **не работала вообще**.

### Причина

Использовалась проверка через headless-браузер и поиск класса
`closed_comments` в HTML. Оба допущения оказались ложными:

1. **`closed_comments` есть у всех публикаций.** Реальная разметка:
   ```html
   <div id="post-65967716_947" class="_post post page_block post--with-likes
        closed_comments deep_active Post--redesign ...">
   ```
   Это служебный флаг VK, а не признак закрытых комментариев. Проверено
   сравнением закрытого и открытого поста — класс присутствует у обоих.

2. **Мобильная версия не рендерит комментарии для анонимов.** У `m.vk.com`
   нет ни `wall_replies`, ни `closed_comments`, ни текста «ограничил
   возможность» — ни для закрытых, ни для открытых постов.

3. **`detect_closed` считал наличие `wall_post` доказательством «открыто».**
   Поскольку `wall_post` есть всегда, функция **всегда возвращала `OPEN`**.

Ранее заявленные «4/4 верных определения» были случайным совпадением: все
четыре поста были открытыми.

### Решение: `wall.getComments` → `can_post`

Перебор методов API дал рабочее решение — поле **`can_post`** в ответе
`wall.getComments`. Оно доступно сервисному ключу:

| Публикация | `can_post` | Проверка |
|---|---|---|
| `-65967716_947` (автор ограничил) | **False** | ✅ |
| `-238001933_6418` | True | ✅ |
| `-33872127_32845` | True | ✅ |
| `-1_400529` (28 комментариев) | True | ✅ |
| `-1_400458` (69 комментариев) | True | ✅ |

**5/5 верно**, время проверки — **0.22–0.38 с** вместо 2–7 с с браузером.

### Защита от повтора

`interpret_response()` доверяет только строгому `bool`:

* `{"can_post": False}` → `CLOSED`
* `{"can_post": True}` → `OPEN`
* поле отсутствует, `"false"`, `0`, `1`, не-словарь → `UNKNOWN` (публикация
  сохраняется, ошибка пишется в `monitoring_runs.errors`)

Так изменение формата ответа VK не приведёт к массовому отбрасыванию
публикаций — проверка деградирует в fail-open, а не в ложные отказы.

только ближайший пропущенный слот.

недоставленных сообщений не зависят от окон поиска.

### Найденные проблемы и решения

**1. Валидатор не засчитывал падежные формы.** Комментарий «роботы» не
совпадал с «роботов» в публикации → проверка `relevance` проваливалась →

на haiku вылезло сразу.

Решение: `_stems()` — сравнение по основе слова (отбрасывается 1–2 символа).
Теперь «роботах», «роботов», «роботы» считаются совпадением.

**2. Быстрая модель хуже держит лимит длины.** Комментарии выходили 331–345
символов при лимите 300 → полная регенерация.

Решение: `_trim_to_limit()` — перед валидацией текст подрезается по границе
предложения. Если после подрезки он короче минимума, возвращается исходный
(тогда решает валидатор).

**Итог улучшений:** валидных комментариев 2/3 → **3/3**, попыток 1.67 → **1.33**,
время 49.5 → **43.1 с** на публикацию.

**3. `gen_prod_env.py` при обновлении ломал доступ к БД.** Скрипт генерирует
новый пароль каждый запуск — при повторном использовании пароль в `.env`
разошёлся с паролем в volume PostgreSQL, контейнер падал в цикле
`password authentication failed`.

Решение: добавлен `scripts/update_env.py` — обновляет `.env`, **сохраняя**
существующий пароль БД. `gen_prod_env.py` остаётся только для первой установки.

## Свежесть публикаций и суточный лимит LLM

Изменение по требованию заказчика: обрабатываются только свежие публикации,
а LLM задействуется не более 25 раз в сутки.

### Что изменилось

| Параметр | Было | Стало |
|---|---|---|
| Расписание (МСК) | 10, 11, 18, 19 | **10, 11, 12, 17, 18, 19** |
| Возраст публикации | не ограничен | **не более 4 часов** |
| Лимит LLM | 150 за цикл | **25 в сутки** |

### Как работает

**1. Сбор в PostgreSQL.** Каждый цикл ищет публикации по маркерам в окне
`[now − 4 ч, now]`. Перед сохранением `filter_fresh_posts()` отбрасывает всё,
что старше `monitoring.max_age_hours`, — старые посты в базу не попадают.
Публикации с датой «из будущего» (ошибка часового пояса источника) тоже
отбрасываются.

**2. Очередь в PostgreSQL.** Публикации сохраняются со статусом `new`.
Цикл берёт их по очереди — от старых к новым (`ORDER BY published_at`),
сначала остаток с прошлых циклов, потом свежую выборку.

**3. Проверка перед LLM.** Непосредственно перед каждым запросом к LLM
проверяется возраст: цикл может идти долго, и к моменту обработки публикация
способна выйти за 4-часовое окно. Устаревшая публикация пропускается, токены
не тратятся.

**4. Суточный лимит.** `llm.max_posts_per_cycle = 25` — это лимит **на сутки**,
а не на цикл. Счётчик живёт в Redis (`llm:daily_usage:<дата МСК>`) с TTL до
полуночи: в новый день лимит возобновляется автоматически. Место
резервируется атомарным `INCR` перед каждым запросом, поэтому лимит
соблюдается всеми циклами вместе.

## Очистка БД от отработанных публикаций

Требование заказчика: база данных не должна раздуваться.

### Что удаляется

Публикация удаляется, когда она **полностью отработана** — выполнены оба условия:

1. статус терминальный: `sent`, `rejected_ad`, `rejected_filter`,
   `rejected_llm`, `rejected_comment`, `failed`;
2. с момента обработки прошло не меньше `db.retention_hours` (24 ч).

Вместе с публикацией каскадно удаляются `post_analysis`, `post_markers`
и `notifications` (`ondelete="CASCADE"` в моделях + явный `DELETE`
уведомлений для корректной статистики).

### Что НЕ удаляется никогда

| Статус | Почему |
|---|---|
| `new` | ждёт обработки LLM |
| `approved` | прошла LLM, ждёт проверки комментариев |
| `queued` | стоит в очереди Telegram |

Незавершённая работа сохраняется независимо от возраста — иначе публикация
потерялась бы недоставленной.

### Зачем запас 24 часа

- **дедупликация**: тексты последних публикаций (`load_seen_texts`, 300 шт.)
  служат контекстом для поиска повторов. Если удалить всё сразу, одинаковые
  рекламные тексты снова пойдут в LLM;
- **отложенные уведомления**: при сбое Telegram попытки повторяются, запись
  должна существовать;
- **разбор спорных отклонений**.

### Где вызывается

В начале каждого цикла, до сбора текстов дедупликации — чтобы старые записи
не попадали в контекст фильтров. Ошибка очистки не роняет цикл: она пишется
в `counters.errors["db_cleanup"]` и работа продолжается.

Удаление идёт пачками по `db.batch_size` (500), чтобы не держать долгую
транзакцию на большой базе.
